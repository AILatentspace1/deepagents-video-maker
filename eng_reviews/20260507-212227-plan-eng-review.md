## Architecture review

### 1. Render/package tools can still be called out of milestone order

**Finding:** `vm_render_remotion_project` and `vm_package_render_output` load `state.yaml` and execute directly; unlike `vm_start_build_scenes` and `vm_start_render_package`, they do not check that `render_package` is `in_progress` or that `build_scenes` is `completed` at call time.

**Risk:** A Producer or model can accidentally render/package stale files from `remotion-project/out` without having entered the Render Package milestone, producing a final artifact that looks valid while `state.yaml` does not prove the workflow path was followed.

**Recommendation:** Add deterministic guards inside `render_remotion_project()` / `package_render_output()` or their LangChain wrappers: require `build_scenes=completed` and `render_package=in_progress`, then add regression tests for direct out-of-order calls.

### 2. Workflow completion is not represented in `workflow_status`

**Finding:** `ratify_and_update_render_package()` marks the `render_package` milestone completed but does not update `VideoMakerState.workflow_status` to `completed`. `save_state_yaml()` also only serializes milestone scalar fields and never persists the ratify payload embedded on `MilestoneState`.

**Risk:** A completed video run can still read as `workflow_status: in_progress`, forcing downstream automation/UI to infer completion from milestones and separate ratify JSON files.

**Recommendation:** When Render Package ratify passes, set `state.workflow_status = WorkflowStatus.COMPLETED`; consider persisting compact ratify summary fields or documenting that ratify JSON files, not `state.yaml`, are the durable audit source.

### 3. `video-maker-v2` skill still documents Generate Audio, but native runnable path skips it

**Finding:** `skills/video-maker-v2/SKILL.md` describes `Setup → Source Intake → Script → user script review → Generate Audio → Build Remotion Project → Render & Package`, and references `audio-contract.md`; the native tool chain and AGENTS runnable path go directly from Script approval to Build Scenes.

**Risk:** Operators following the project-level skill may expect audio artifacts, duration measurement, and `audio_manifest` consumption, while the native DeepAgents path neither creates nor ratifies those artifacts.

**Recommendation:** Choose one contract: either add an explicit Audio milestone/tool layer or update skill docs to mark Generate Audio as optional/deferred for the current native path. Do not leave it as a default step unless it is represented in state and tests.

## Code quality review

### 4. Final video ratify is too weak for the acceptance criteria

**Finding:** `ratify_render_package()` checks only `final/video.mp4` exists and is non-empty; the workflow contract and skill acceptance criteria mention `ffprobe` duration validation and target duration-band acceptance.

**Risk:** A corrupted or wrong-duration MP4 can pass native ratify as long as it has bytes, causing false-positive completion.

**Recommendation:** Add an optional `ffprobe` command runner seam and ratify duration against `goal.target_duration_seconds` / duration band, with a clear warning-vs-blocking policy if `ffprobe` is unavailable.

### 5. Build Scenes ratify validates skeleton, not renderability

**Finding:** `ratify_build_scenes()` currently checks only `remotion-project/package.json` and `src/index.ts`. TypeScript/render validation happens later in `render_remotion_project()` and its command results are returned but not persisted as milestone ratify evidence.

**Risk:** The Build Scenes milestone can be marked completed for a non-compiling project; later render failures become harder to connect to the build milestone that introduced them.

**Recommendation:** Keep the lightweight skeleton check if fast iteration is desired, but persist render/tsc command results to `ratify/render-command.json` and consider a stricter optional Build Scenes check for `pnpm exec tsc --noEmit`.
